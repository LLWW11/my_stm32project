## 六、跨端联动（bootloader 之外必须同步的三件事）

这是“三方合同”，bootloader 改完只是三分之一：

1. APP 侧 `can_iap_task` 的 END 分支

   （我上一轮给你的代码）同步三处：

   - 头部缓冲从 20 字节写成 24 字节（`magic/target/length/image_crc/version/header_crc`，state 位保持 0xFF）；
   - `iap_put_u32_le(&header[16], version)` 填入版本；
   - `header_crc` 计算从 `boot_crc32(header, 16)` 改成 `boot_crc32(header, 20)`；state 提交从 `+20` 改成 `+24`。

2. **version 的值从哪来**——注意一个逻辑陷阱：**头部里的 version 描述的是“正在接收的新镜像”，而写头部的是正在运行的旧 APP**，旧 APP 不可能知道新镜像的版本。所以 version 必须由 6ULL 通过 CAN 下发。START 帧 8 字节已经被 length+crc 占满了，建议阶段二新增一帧 `0x126 META`（DLC 4，纯 version，在 START 之后、第一帧 DATA 之前发，STM32 存进 ctx 再在 END 时写头部）。这一帧暂时可以不做，但**字段布局必须现在定死**，否则以后改布局又是一轮三方联动。

3. **文档**：`bootloader/W25Q128镜像安装说明.md` 里写死了“24 字节、六个 32 位字段”，要同步改成 28 字节、七个字段，并把 version 的字节序（小端）和编码约定写进去。

版本号编码建议用宏固定下来，放 `boot_update.h`（顺便给将来 APP 共用）：

c

```c
// 版本编码：高16位主版本、次8位次版本、低8位修订号，如 v1.2.3 = 0x00010203
#define BOOT_VERSION_ENCODE(major, minor, patch) \
    ((((uint32_t)(major)) << 16) | (((uint32_t)(minor)) << 8) | ((uint32_t)(patch)))
```

## 七、验证步骤（上板走一遍）

1. 编译 bootloader，0 错误；烧录后不放镜像，串口应还是正常走到 "APP valid / Stay in bootloader"（回归确认没伤到旧路径）。
2. 用旧工具往 W25 手工放一个 **v1 格式（24 字节头）** 的 READY 镜像 → 期望：**不安装**（CRC 覆盖长度对不上）——这恰好验证了新校验生效。
3. 手工构造一个 v2 头（28 字节，version 填 0x00010203，header_crc 按前 20 字节算）+ 正文镜像 → 期望：打印 version、安装成功、DONE 写入后回读一致、复位进新 APP。
4. 故意把 version 留 0xFFFFFFFF → 期望被 `boot_header_valid()` 拒绝。
5. 用万用逻辑/串口日志确认安装后**只复位一次**（防无限重装循环）。
