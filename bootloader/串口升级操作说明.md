# WeatherClock 串口暂存升级操作说明

本实验的完整路径为：电脑通过 USART1 发送 APP BIN，Bootloader 将数据写入 W25Q128，复位后将镜像安装到 STM32F407ZG 内部 Flash 的 APP 分区，最后跳转到新 APP。普通 SPI3 连接的 W25Q128 不直接执行代码。

## 地址和串口

| 项目 | 地址或参数 |
|---|---|
| Bootloader 内部 Flash | `0x08000000～0x0800FFFF`，扇区 0～3 |
| APP 内部 Flash | `0x08010000～0x080FFFFF`，扇区 4～11 |
| W25Q128 镜像头 | `0x000000`，24 字节，独占首个 4 KiB 扇区 |
| W25Q128 BIN 正文 | 从 `0x001000` 开始，最多 `0xF0000` 字节 |
| W25Q128 开发自检扇区 | `0xFFF000`，升级期间不应再运行擦写自检 |
| USART1 | PA9 发送、PA10 接收、GND 共地；115200、8N1、3.3 V 电平 |

## 第一次使用的步骤

1. 保存当前可运行的 Bootloader 和旧 APP 烧录文件，并确认调试器能单独恢复它们。升级安装会擦除 APP 分区；如果安装阶段断电，可能需要重新发送镜像或使用调试器恢复。
2. 使用 APP 的 EIDE `f407`、AC5 配置构建新版本。其 IROM 必须是 `0x08010000 / 0x000F0000`。当前 `app/board.c` 已有 `OTA test version: v2` 打印。保留板上旧 APP，不要提前把 v2 直接烧到内部 APP 区。
3. 在 APP 构建结果中找到 BIN。若只有 AXF，可以执行 `C:\Keil_v5\ARM\ARMCC\bin\fromelf.exe --bin --output v2.bin weatherClock.axf`；实际 AXF 路径按构建输出调整。BIN 没有目标地址信息，发送脚本会检查其前两个向量，Bootloader 固定将其写到 `0x08010000`。
4. 构建 `bootloader/mdk/weatherClock_bootloader.uvprojx`，当前构建结果应为 `bootloader/mdk/Objects/weatherClock_bootloader.hex`。烧录 Bootloader 时选择按扇区擦除，核对下载工具没有整片擦除内部 Flash，避免提前抹掉旧 APP。烧录后复位，确认仍能正常输出 5 秒倒计时并启动旧 APP。
5. 电脑安装 `pyserial`：`python -m pip install pyserial`。先关闭占用同一串口的串口监视器；同一电脑串口只能由一个程序打开，发送脚本在升级期间兼任串口日志窗口。确认 BIN 和串口号后，在项目根目录运行：`python tools/send_boot_update.py COM5 路径\到\v2.bin`。脚本会在打开串口前将 DTR、RTS 均设为 inactive；此设置与本板上可正常复位并输出日志的 `miniterm --dtr 0 --rts 0` 一致。脚本启动后按照提示复位开发板。
6. 脚本看到 Bootloader 的 `Send U` 提示后自动发送 `U`，等待 `[BOOT] RX READY`，然后发送 BIN。它会显示 Bootloader 的 W25 擦除进度、每 32 KiB 的回读校验进度和每包 ACK 后的确认字节数。完整暂存成功后应出现 `[BOOT] STAGED OK`。设备自行复位，启动时应输出 `W25 image READY`、`External CRC PASS`、`Internal CRC PASS`、`Install PASS`，再次复位后出现 `OTA test version: v2`。
7. 若停在“请现在复位开发板”且完全没有 `[BOOT]` 行，先按板上的 NRST。仍无输出时停止脚本，运行 `python -m serial.tools.miniterm COM5 115200 --dtr 0 --rts 0` 独立检查启动日志；若能看到旧版启动日志却没有 `W25 UART updater WUP1`，需核对新版 Bootloader HEX 是否真正烧入。脚本现在会在 10 秒无数据时提示检查这些条件，也会识别安装失败后驻留模式的 `Send U` 提示。
8. 再次断电上电，确认不会重复安装，并能正常进入 v2 APP。

`pyserial` 只用于电脑端发送脚本，不需要加入 MCU 工程；能运行上述 `miniterm` 命令的 Python 环境已安装此依赖。

## 简化传输协议

1. Bootloader 启动窗口内收到 ASCII `U` 后输出 `[BOOT] RX READY`。
2. 电脑发送 12 字节开始帧：`WUP1`、32 位小端 BIN 长度、32 位小端整包 CRC32。Bootloader 擦除 W25 镜像头和需要的正文扇区后回复单字节 `K`。
3. 电脑每次发送最多 256 字节正文，后跟这个数据包的 32 位小端 CRC32。Bootloader 校验数据、写入 W25、读回逐字节比较后回复 `K`，每 32 KiB 额外输出一行接收进度日志。发送脚本会同时解析日志与 `K`，显示的是设备已回读确认的进度。收到错误日志或等待超时，电脑脚本停止；本版协议从头重新发送，不做中途续传。
4. 全部数据写完后，Bootloader 重读 W25 并计算整包 CRC32，检查 BIN 的 MSP 和 Reset_Handler，最后写入 24 字节镜像头和 `READY` 状态，再复位。
5. 复位后只安装 `READY` 镜像。Bootloader 先校验外部镜像，再擦除内部 APP 扇区 4～11，分块写入正文；首 8 字节向量留到最后写。内部 CRC32 正确后将状态从 `READY` 写成 `DONE` 并复位。状态更新仅把 NOR Flash 的位从 1 改为 0。

CRC32 使用常见的 CRC-32/ISO-HDLC 参数：反射多项式 `0xEDB88320`，初值 `0xFFFFFFFF`，输出异或 `0xFFFFFFFF`；与 Python `binascii.crc32()` 一致。

## 失败处理和当前边界

- 首次安装前若发送中断、包 CRC 错误或 W25 写入失败：新镜像不会进入 `READY`，旧内部 APP 仍在；复位后可重新发送。若此前已发生安装失败，旧 APP 可能已经部分擦除，应留在 Bootloader 中重新发送或使用 SWD 恢复。
- 外部镜像 CRC 错误：Bootloader 在擦除内部 APP 之前拒绝安装。
- 内部 APP 擦写失败或中途断电：镜像头仍为 `READY`，再次启动会尝试重装。若 W25 也出现故障，可通过 SWD 重新烧录 Bootloader 与 APP。
- 这是用于首次闭环验证的单镜像升级方案，没有双镜像回滚、加密签名或传输断点续传。CRC32 检查误码，不证明固件来源可信。
- 目前只有本机编译和脚本语法验证，串口收发、扇区擦写、断电恢复还需要在真实开发板上按上述日志验收。
