交叉编译之后将 `can_iap_send` 与待升级 `weatherClock.bin` 复制到 i.MX6ULL，然后执行如下指令：

```shell
chmod +x ./can_iap_send
./can_iap_send --file ./weatherClock.bin --dry-run

ip link set can0 down
ip link set can0 type can bitrate 500000 restart-ms 100
ip link set can0 up
ip -details -statistics link show can0

./can_iap_send --interface can0 --file ./weatherClock.bin
```

STM32 的位时序要求 APB1 为 42 MHz：`42 MHz / (6 × (1 + 11 + 2)) = 500 kbit/s`



约定can帧格式：

| 报文       | DLC  | Data布局                                                     |
| ---------- | ---- | ------------------------------------------------------------ |
| 启动 0x120 | 8    | [0..3] BIN 长度；[4..7] BIN 的 CRC32                         |
| 数据 0x121 | 5~8  | [0] 会话号；[1..3] BIN 偏移；[4..] 本帧 1～4 字节固件        |
| 终止 0x122 | 5    | [0] 会话号；[1..4] BIN 长度                                  |
| 回复 0x123 | 8    | [0] 状态；[1] 会话号；[2..4] 下一期望偏移；[5] 错误码；[6] 请求 ID 低字节；[7] 0xA5 |

 查询与版本帧暂未实现，本任务目前只接受 START、DATA、END

## 中断后继续发送

使用适配续传的发送程序，并确保 STM32 APP 包含会话绑定修正及 I2C1 初始化修复。中断后恢复连接，距最后一帧等待超过三秒，使 STM32 回到 IDLE；若按 RESET，则等待 IAP 初始化完成，再执行同一 BIN 的发送命令：

```shell
sleep 4
./can_iap_send --interface can0 --file ./weatherClock.bin
```

不需要新增参数或主机断点文件。START ACK 会返回 STM32 的 AT24C02 检查点，发送端显示 `RESUME offset=...` 并从这里继续。记录每约 4 KiB 或正文收齐时保存，可能重发检查点之后的数据；EEPROM 不可用、记录无效或 BIN 的长度/CRC 已变化时，从零开始。

正文已收齐但未提交时，先重发最后一个字节绑定新会话，再发送 END。若 END 结果未确认（退出码 2），先看串口确认是否已经 READY 或安装完成，避免盲目重跑。详细协议、主机测试和板端反馈见同目录 `README.md`。

## EEPROM 初始化故障与已验证结果

2026-10-06 用户已验证：删除 `my_driver/board/IIC.c` 中 `IIC1_Init()` 末尾的 `(void)IIC1_BusRecover();` 调用后，传输中按 STM32 RESET 再续传恢复正常，修复已提交 Git。当前函数仍保留，初始化不再调用。

修复前的 `[IAP] AT24C02 missing, resume disabled` 表示 EEPROM 探测失败，接收期间不会保存断点，所以复位后只能重新 START 从零发送。续传前应看到 `[IAP] AT24C02 OK, resume enabled`，有效断点恢复时看到 `[IAP] RESUME from ...` 和发送端 `RESUME offset=...`。

本次确认的是用户反馈的 RESET 续传；EEPROM 更新期间实际断电、安装阶段中断恢复及长期稳定性仍需单独验证。
